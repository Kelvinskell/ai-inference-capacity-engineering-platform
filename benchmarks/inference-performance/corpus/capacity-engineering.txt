Inference capacity engineering connects workload behavior to the limits of the serving system. A useful investigation begins with a stable model artifact, a pinned serving image, a known accelerator, and a workload whose input and output sizes can be reproduced. The operator changes one meaningful dimension at a time and records both client-visible behavior and server-side telemetry.

Request concurrency is not the same as scheduler concurrency. Clients may hold many requests open while the serving engine admits only a subset as active sequences. Requests beyond that admission limit wait in a queue. At low load, latency is dominated by prompt processing and token generation. Near saturation, queue delay grows, tail latency separates from median latency, and additional clients may stop increasing useful throughput.

Prompt processing and token generation stress different parts of the accelerator. Prefill consumes a large batch of input tokens and can produce short bursts of high compute utilization. Decode processes fewer tokens per sequence at each iteration but repeatedly reads model weights and key-value cache state. A workload with long prompts and short outputs emphasizes prefill, while short prompts with long outputs emphasize decode.

The key-value cache stores attention keys and values for tokens retained by active sequences. Its capacity depends on memory remaining after model weights, runtime allocations, and other buffers are placed on the accelerator. Increasing the configured GPU memory utilization can expand the cache budget, but it also reduces safety margin for temporary allocations and may increase the risk of out-of-memory failures.

Maximum model length defines the largest combined context the engine will accept for one request. The combined context includes input tokens and generated output tokens. Configuring a large maximum does not prove that the workload can use it efficiently. Tests must submit prompts near the selected limits and reserve enough context for the requested output. A configuration that starts successfully can still support very little concurrency when each sequence consumes a large share of the cache.

Continuous batching combines work from multiple requests into scheduler iterations. The maximum number of sequences limits how many requests may be active, while the batched-token ceiling limits token work admitted in an iteration. Small ceilings can protect latency but underuse the accelerator. Large ceilings can improve throughput while increasing iteration time and tail latency. The useful setting depends on prompt shape, output shape, and service objective.

A controlled benchmark separates warmup from measurement. Warmup allows model kernels, memory pools, connections, and caches to reach a representative state. The measurement interval then records completed requests, failures, latency distributions, token throughput, queue depth, cache utilization, and accelerator activity over the same timestamps.

Tail latency is often the earliest visible sign of saturation. Median latency may remain stable while the slowest requests wait behind large prefills or long-running decode sequences. Percentiles should be calculated from successful requests, while timeout and error durations should be reported separately. Successful request rate and generated-token rate provide different views of throughput and should not be substituted for each other.

Reproducibility requires more than preserving a command. Every result should identify the model revision, serving image, accelerator, deployment arguments, workload dimensions, route, benchmark duration, and source revision. Generated request logs are local runtime artifacts, while reviewed reports should preserve the selected evidence and explain the conditions under which it was measured.

Prefix reuse can make repeated prompts appear cheaper than independent production requests. A benchmark intended to measure raw cache pressure should vary request content near the beginning of each prompt and observe prefix-cache metrics. Cache-focused experiments may deliberately repeat prefixes, but those runs must be labeled separately so their results are not confused with independent-request capacity.

An inference gateway adds authentication, routing, rate limiting, retries, and transport overhead. Direct predictor tests isolate the model server, whereas gateway tests measure the complete serving path. Both can be useful, but the selected route must be recorded because their latency and failure behavior answer different engineering questions.

Capacity recommendations should identify a stable operating envelope rather than only the largest observed number. A useful envelope states the workload shape, acceptable tail latency, sustained token throughput, error budget, queue behavior, and memory margin. It also explains what changes first when demand exceeds that envelope and which telemetry should trigger scaling or admission control.
